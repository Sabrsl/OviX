## 3. AMBIGUÏTÉ IDENTIFIÉE

### Problème
`analysis_results.status='pending'` signifie "analyse terminée, en attente de décision utilisateur"
Mais 'pending' est aussi utilisé pour "en attente d'analyse" dans d'autres tables

### Impact
- Confusion sémantique dans le modèle métier
- Difficile de distinguer "analyse terminée" vs "en attente d'analyse"
- Risque d'erreurs dans le workflow

---

## 4. MODÈLE PROPOSÉ (OPTION 1 - RECOMMANDÉ)

### Solution
Renommer `analysis_results.status='pending'` → `'awaiting_decision'`

### Migration SQL
```sql
UPDATE analysis_results SET status = 'awaiting_decision' WHERE status = 'pending';
```

### Impact Backend
- backend/api/routes/articles.py:452 → status="awaiting_decision"
- backend/api/routes/history.py:260 → WHERE status = 'awaiting_decision'
- backend/stats/repository.py:43 → COUNT(analysis_results WHERE status='awaiting_decision')

### Impact Frontend
- frontend/src/api/types.ts:116 → Ajouter 'awaiting_decision'
- frontend/src/components/ArticleHistory.tsx:52 → Ajouter 'awaiting_decision'
- frontend/src/components/ArticleStatusCard.tsx → Ajouter cas 'awaiting_decision'
- frontend/src/pages/AnalyzedHistory.tsx → Ajouter STATUS_META['awaiting_decision']

### Avantages
- ✅ Résout l'ambiguïté principale
- ✅ Faible risque de régression
- ✅ Migration simple (un UPDATE)
- ✅ Compatible avec l'architecture existante
- ✅ Pas besoin de modifier le schéma
